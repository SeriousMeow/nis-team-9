# План эксперимента

## Проверяемый вопрос

Явное описание алгоритма на уровне блоков вместе с компиляторными преобразованиями позволяет безопасно получать специализированные конвейерные коллективы без ручного написания низкоуровневого GPU-кода.

## Сравниваемые варианты и baseline

В качестве baseline используем авторские реализации ring AllReduce и AllToAll из библиотеки `msccl-tools` со стандартными настройками и отключённым слиянием инструкций.

С baseline сравниваем варианты с изменёнными параметрами и собственные реализации этих коллективных операций. Для каждого варианта фиксируем отличия от baseline.

Сравнение проводим при одинаковых входных данных, топологии и правилах расчёта стоимости операций. Параметры, не относящиеся к исследуемому изменению, сохраняем одинаковыми.

Корректность всех вариантов, включая baseline, проверяем сравнением с независимо вычисленным ожидаемым результатом. Для корректных расписаний сравниваем число инструкций каждого типа и модельное время выполнения.

## Данные или нагрузки

Внешних данных нет. Будут вручную подготовлены программы на Python для `msccl-tools` и примеры корректных и некорректных XML для указанных алгоритмов. Точные параметры будут определены позднее.

## Конфигурации и план запусков

Запуски выполняем на локальном компьютере в окружении проекта с зафиксированными зависимостями.

Предварительно рассматриваем изменение настроек слияния инструкций, модели стоимости операций, топологии и реализации коллективной операции. Дополнительно исследуем доступные параметры компиляции. Окончательный набор параметров и их значения определяем после изучения возможностей компилятора и пробных запусков, до основной серии экспериментов.

Сначала проверяем работу baseline, затем исследуем отдельные изменения относительно него. Внутри каждого сравнения сохраняем одинаковыми входные данные и остальные условия. При изменении топологии или модели стоимости повторно рассчитываем baseline в тех же условиях.

При детерминированном выполнении повторные запуски одной конфигурации для оценки модельной стоимости не требуются. Возможное расширение эксперимента — случайные колебания стоимости операций и изменение порядка выполнения доступных инструкций. В таком случае проводим серию запусков, сохраняем начальные значения генератора случайных чисел для воспроизводимости и анализируем разброс метрик и результаты проверки корректности. Число повторов определяем по результатам пробных запусков.

## Метрики

Каждой операции назначаем стоимость в условных тактах. Симулятор учитывает порядок инструкций и ожидания зависимостей. Измеряем суммарную стоимость операций по каждой GPU и модельное время завершения всего расписания. Стоимости операций и правила учёта параллельности фиксируем перед экспериментами.

## Проверка корректности

Проверяем отдельные операции симулятора юнит-тестами. Для корректных расписаний AllReduce и AllToAll сравниваем конечные буферы с независимо вычисленным ожидаемым результатом. Проверяем обнаружение потерь, дублирования, чтения до записи и взаимоблокировки не менее чем на трёх намеренно испорченных расписаниях.

## Обработка и анализ

Для каждого запуска сохраняем конфигурацию, результат проверки корректности, число инструкций каждого типа и рассчитанные значения метрик. При обнаружении ошибки сохраняем диагностическую информацию для её воспроизведения и разбора.

Сравниваем корректные расписания с эталонным при одинаковых входных данных и условиях моделирования. Анализируем различия в числе инструкций каждого типа и модельном времени выполнения, объясняем их связь с устройством расписаний.

Для намеренно испорченных расписаний сопоставляем ожидаемые ошибки с обнаруженными. Отдельно разбираем случаи, когда ошибка не обнаружена или корректное расписание отклонено.

По результатам анализа формулируем выводы о корректности исследованных расписаний и их стоимости в принятой модели, указываем ограничения выводов.
